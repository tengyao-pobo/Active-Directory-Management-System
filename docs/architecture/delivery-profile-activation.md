# Delivery profile activation boundary (proposal; inactive)

Profile 4 is not ready to activate. The history SQL and catalog checks are staged artifacts. Neither a passing catalog audit nor the delivery pool's closed external audit proves that every existing execution path is closed between installation and history validation.

## Authority and transaction boundary

The installer assigns functions to separate NOLOGIN definers. A restricted application table owner cannot perform these ownership transfers without additional authority over those roles. Retaining role memberships conflicts with the exact capability profile. Existing installers also require expected owner = CURRENT_USER, so the privileged executor versus final restricted owner must be resolved explicitly; a test-only ownership transfer is not a production installation procedure. A second physical LOGIN cannot inspect uncommitted installation DDL, so a privileged installer transaction and a physically authenticated owner audit cannot share one transaction.

The intended design therefore requires two durable phases:

1. The reviewed privileged installation transaction takes the exclusive profile advisory lock, installs the exact candidate profile and commits a database-enforced PendingHistoryAudit state. All execution, queue, status and delivery entrypoints must reject that state before operational data access. New delivery pair grants should be deferred where the complete installation contract permits it.
2. A separate physical restricted owner LOGIN takes the same exclusive lock and the history audit's nine relation locks, attests the maintenance structure, validates complete history visibility and row consistency, and atomically records Ready with a final audit. Failure leaves PendingHistoryAudit committed and all runtime entrypoints closed.

For reinstallation of an already-active profile, the physical owner must first commit Ready generation N to PendingHistoryAudit generation N+1 with a new nonce under the exclusive profile lock. Installation and a fresh owner audit follow. An identical Pending generation/nonce/digest may be retried; a different Pending tuple must fail. Never blindly overwrite it with ON CONFLICT.

A C# readiness flag, service shutdown, cooperative maintenance convention, or closed delivery pool alone cannot enforce this boundary against direct SQL calls. The state must be bound to the exact installation generation; a previous successful audit must never approve a later installation.

After phase 1 commits, recovery is fail-closed repair/retry or an explicitly designed downgrade. It is no longer a single-transaction rollback to profile 3. The existing rollback-only upgrade fixture still proves only pre-commit rollback behavior.

## Required evidence before consumption

- Exact singleton state relation, constraints, ownership, ACLs and transition semantics; runtime roles have no direct state-table privileges.
- Pinned gate and transition guard ABI, owner, configuration, ACL and body, with the actual Ready transition inside the history DO rather than a standalone ready setter; separate owner maintenance structural attestation while Pending.
- Physical runtime LOGINs reject both audits and direct production wrappers after privileged installation commits Pending.
- Physical restricted owner validation commits Ready only for the current installation generation; malformed history leaves Pending.
- An active runtime transaction holding the shared profile lock blocks phase 1. Phase 2 cannot approve a concurrent replacement installation.
- Failure, retry, repeated installation, nonce mismatch and privilege/structure drift remain closed, with verified cleanup and no retained installer memberships.

The accompanying unconsumed enrollment-profile4-readiness.sql currently stages only the singleton relation and transition guard. A disposable physical-owner test checks shape, invalid transitions, exclusive-lock requirements and direct runtime denial. The owner is the database trust root and can alter its objects: the guard alone cannot prove a history scan ran. The independent source manifest and owner-only ready predicate are now staged separately. The manifest uses a versioned header and ordered filename/SHA-256 pairs over LF-normalized UTF-8 sources: the six journal/status structure slices, history-row query and readiness schema. These roots exclude the generated predicate and composed audits, preventing circular hashing. This is a history-attestation contract manifest, not a digest of all installed profile DDL. Every reviewed install/reinstall must close with a new generation/nonce even when these eight roots are unchanged; ordinary audits must still attest all live functions, bindings, identities and privileges. The predicate supplements live catalog checks; it is not trusted until its exact ABI/body/ACL and table metadata are attested. The owner-only maintenance/runtime split and pinned owner history transaction are now staged and tested with physical LOGINs. These candidates remain unconsumed by the actual installer. They do not establish complete activation readiness.

## Selected installer authority model (candidate design)

The first installation candidate will require a trusted, physically authenticated PostgreSQL superuser executor, with SESSION_USER=CURRENT_USER. This executor is distinct from the final owner and every API/plan-lock/execution/queue/status/delivery capability identity. This explicitly models the authority needed to transfer objects to unrelated zero-membership NOLOGIN definers. It does not make the restricted owner temporarily assume those roles. Managed services without true SUPERUSER require a separately reviewed provider-specific design.

The final owner is a distinct LOGIN with NOSUPERUSER, NOBYPASSRLS, NOCREATEDB, NOCREATEROLE, NOINHERIT and NOREPLICATION and zero inbound/outbound memberships. After installation it must own the named database, enrollment_execution schema and exact application object manifest, including the Environments anchor. Preserve public schema and extension ownership. Transfer only explicitly enumerated objects to their expected owners; reject missing/extra objects and unexpected source owners. Never use REASSIGN OWNED or leave installer-owned application objects or capability memberships behind.

Initial/v3 phase 1 must hold the exclusive profile lock, install the complete gate and exact Pending generation 1/new nonce/current history manifest, assign all final owners/ACLs, and commit atomically. Reinstallation instead requires the physical final owner to commit the next Pending tuple before privileged installation; the executor must verify that exact tuple without replacing it. Privileged postflight pins and invokes maintenance for all Execution bindings and requires ordinary execution audits to remain false/ProfileDrift/4. Old postflights expecting ordinary true cannot be reused while Pending, and delivery audits bind SESSION_USER to the real runtime purpose.

Failure before initial phase-1 commit rolls back to v3. Failure after a pre-closed reinstall leaves the prior committed Pending state. Once phase 1 commits, history failure is repair/retry while Pending, never an automatic downgrade or fallback to a superuser history scan. The separate restricted-owner bootstrap is the only proposed history activation entrypoint. This design trusts the deployment administrator; it does not defend against a malicious cluster superuser.

Before implementing an executable phase-1 installer, complete the exact object manifest and API database publication barrier. The current 9/3/3 runtime inventory now also scans effective sequence USAGE/SELECT/UPDATE privileges separately from table/view/column privileges. Those disposable tests and the selected authority model were reviewed by Daybreak; they do not authorize enterprise database changes or enable the external gate.

## Serializable snapshot correction (candidate)

A real runtime regression reproduced a stale Ready snapshot: a SERIALIZABLE transaction established its snapshot, the physical owner committed Pending, and the existing queue wrapper still accepted the old audit result. Shared advisory acquisition alone does not refresh a transaction snapshot. This was an activation blocker in the inactive candidate.

The candidate ordinary execution audit is now VOLATILE and first attempts the shared transaction advisory lock without waiting. If another transaction owns exclusive, a direct audit returns false/ProfileDrift/4 immediately. After pinning and successfully running maintenance, it locks the singleton readiness row FOR SHARE without filtering by state. PostgreSQL raises 40001 when that row changed after a Repeatable Read/Serializable snapshot; a missing row returns false. Only then is the attested Ready predicate used. The outer delivery audit is also VOLATILE. All twelve wrapper bodies retain their original shared-lock-first order and no callable grants are added.

Maintenance separately pins both audit ABIs, owners, volatility and fixed configuration; history pins the updated raw runtime body. The dependency remains acyclic. The physical-owner fixture covers stale snapshots through direct execution audit, queue, status and delivery paths, fresh Pending rejection, direct audit during exclusive owner close, reentrant owner history and volatility drift. The next actual installer test must still cover a runtime session/prepared call predating v3-to-v4 function replacement.

The API final publication transaction now takes the shared profile lock before public-context and plan locks. Its contention tests recheck step-up expiry and processor availability after waiting. This is lock-order preparation; the in-memory availability interface remains false by default and cannot substitute for the operation-INSERT database publication guard and exact queued-anchor attestation still to be composed.

## Database publication candidate

The unconsumed profile4 publication fragment adds an ENABLE ALWAYS BEFORE INSERT trigger to EnrollmentGrantOperations. The owner-only definer function requires origin replication mode, attempts the shared profile lock without waiting, pins the ordinary runtime audit, requires its Ready verdict, and requires the physical SESSION_USER to be the sole bound API identity. Maintenance independently attests the trigger attachment, function ABI, owner, ACL and normalized template; it also rejects API role memberships, privileged attributes and parameter grants. The history transition additionally pins the exact rendered guard before activation. Template → maintenance → runtime → rendered guard is an acyclic hash dependency; maintenance compares the guard's embedded hash to the live runtime body without invoking either function.

The disposable physical API LOGIN exercises a complete Approved-to-Queued plan update, operation insertion and matching outbox commit. Plan-only, outbox-only and operation-without-outbox transactions fail their deferred anchors and roll back all changes. Pending rejects a complete publication with the exact unavailable error and leaves the plan Approved with no operation or outbox. Separate tests cover exclusive owner-lock contention, a committed unpinned runtime body, origin/replica transitions, trigger/function drift and an unbound physical LOGIN. These are database boundary tests with synthetic prerequisites, not end-to-end HTTP authentication or approval evidence.

The original membership helper used row_security=off, which fails under a restricted owner and FORCE RLS. The staged forward fragment preserves its OID, owner and membership predicate, sets row_security=on, and adds a SELECT-only true policy applying solely to the owner. It preserves FORCE RLS and the legacy API and worker policies. Maintenance pins the raw helper body, ABI, exact nine Memberships policy names, PUBLIC policy expressions and complete owner-applicable SELECT policy set. Tests exercise both valid membership checks and complete publication through the real API LOGIN, plus rollback-isolated policy/function drift. No historical migration or archived v3 installer is rewritten.

The deployed provisioning and API catalog consumers still recognize historical profile contracts and remain closed against this candidate. An explicit generated v4 consumer branch, exact ownership installation manifest, preexisting-session upgrade tests and service/authentication integration remain activation prerequisites. The external feature gate stays false and PR42 remains draft.

The two SECDEF policy callees now require exact symmetric ACL sets, including owner as grantor and no grant options. Membership permits owner, Api, plan-lock owner, execution Definer, QueueDefiner and DeliveryDefiner; directory access omits QueueDefiner. An extra grant to an unrelated LOGIN makes maintenance and runtime invalid even when publication would independently reject its physical identity. The membership adaptation checks that CURRENT_USER is the restricted final helper/table owner before adding its owner-only policy. Connector bindings currently force this unconsumed candidate closed: support requires an independently attested connector role and complete capability surface before adding its helper grants to the allowed set. This is an activation prerequisite, not a permanent removal of directory connectors.

## API consumer integration contract

The next catalog consumer will use an explicitly generated v4 branch shared by the operation audit and plan-lock audit, including startup. It will read PostgreSQL catalogs only: no grants on private binding/readiness/history tables and no new callable definer function. Catalog success establishes the expected structural contract; it is not live Ready or proof of the API binding. RLS still controls reads and the exact publication trigger decides whether an INSERT may proceed.

Dispatch must distinguish a complete bootstrap database with no marker-dependent roots, exact legacy v2/v3 markers, an exact v4 marker, and invalid/partial installations. Preserve the legacy base and v2/v3 checks. A missing marker must not disguise surviving audit/reservation/readiness/publication roots, policies or triggers. Unknown bodies, wrong signatures and overloads fail closed.

The v4 resource must pin the marker, runtime audit, rendered publication guard, RLS helpers, owner/definer identities, exact Operations/reservation/shared anchors, seven Operations policies, six local triggers and delivery column grants. Derive identities from canonical function owners and public relation anchors. Full reservation-derived runtime ACL validity remains transitively enforced when the pinned publication guard invokes the pinned runtime/maintenance chain. Under the temporary no-Connector contract, catalog-derived helper grantees must match the same six/five exact ACL sets.

For deterministic expression deparsing, execute the fully qualified v4 query with transaction-local search_path=pg_catalog,pg_temp set by a preceding command. Start and close a read-only transaction when none exists; otherwise use a unique savepoint and always roll back to and release it so the caller's transaction and settings survive success, PostgreSQL errors and cancellation. Rollback cleanup uses a bounded independent token, followed by mandatory provider disposal; failure closes the operation. Never normalize deparse text or rely on CTE evaluation order to change search_path.

Publication closure maps only PostgreSQL 55000 with the exact message `Enrollment grant publication is unavailable.` through nested provider/EF exceptions to the existing `EnrollmentGrantExecutionUnavailable` 503. It is not retried; other invariant errors retain existing handling, 40001 retains fresh authorization/retry behavior, and cancellation propagates. A disposable post-preflight trigger test exercises the provider exception chain and verifies rollback of plan state, operation, outbox and queued audit data; it does not claim v4 HTTP activation.

Its internal enum reserves `pg_catalog,pg_temp` for v4. The callback receives the protected context and must use that context for catalog-only queries. Savepoint cleanup preserves the caller's earlier settings and writes; an owned read-only transaction is always rolled back and disposed. The independent five-second token bounds rollback/savepoint operations, not the provider's subsequent tokenless disposal. Physical API-session tests disable pooling so connection reset cannot conceal restoration failures, and cover false verdicts, PostgreSQL errors, cardinality failure, cancellation, read-only rejection and a successful caller commit after an audit error. The generated v4 resource and dispatch remain unfinished.
